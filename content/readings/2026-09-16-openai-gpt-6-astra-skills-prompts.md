## 為什麼讀
資訊收集箱卡片只有網址、無備註。題材是 skill 描述與 AGENTS.md 去冗，正對到 Simon 維護數十支 skill、且 Claude 與 Codex 共用一份核心規則的日常。

## 摘要
OpenAI 為 GPT-6 Astra 寫的指令整理指南。模型越強，過去為了牽著它走而累積的 skill、AGENTS.md 與任務提示詞反而變成負擔。本篇整理成四個方向：skill 描述要短、只講何時該用；skill 主檔只放路標、細節放附屬檔；AGENTS.md 逐條重審，改成「做什麼任務讀哪份文件」；告訴模型何時要先問再做的那些句子、以及「做到哪算完」，都要隨模型重新校準，否則更守規矩的新模型可能過度保守而提早停。

## 核心概念
- [[skill-description-precision]]：skill 的名稱與描述會常駐在模型脈絡裡，當「該不該載入這支」的路標。描述太長、skill 太多時 Codex 會自動截短每支描述，模型看到的資訊變少、更難挑對；描述之間互相矛盾或過度強調「要用我」，會讓模型載入幫不上忙的指令。OpenAI 的例子：「用於資料庫、查詢、模型、持久層」太寬，「新增或修改資料庫遷移（migration）、或審查其上線時」才是對的寫法。（OpenAI 開發者部落格）
- [[progressive-disclosure]]：讀 skill 是有成本的，每讀一段就更接近脈絡壓縮（對話塞滿後系統自動把前文摘要掉、細節會丟）、也可能帶進不相干的指引。所以多流程的 skill 要把根文件做成最小路由器，只告訴模型「哪種情況去讀哪份附屬文件或腳本」。AGENTS.md 同理：「每次編輯前先讀 A、B、C 三份文件」會燒掉脈絡、拖慢工作；改成「服務邊界看 A、資料表結構（schema）改動看 B、部署看 C」才是條件式指向。（OpenAI 開發者部落格）
- [[model-upgrade-instruction-audit]]：換模型時把既有指令整批重審的做法，因為為舊模型累積的指令在更強的模型上可能從幫助變成限制。文章列三類最常過時的指令：①食譜式的過度具體步驟（模型已能處理細微差異）；②催它跑測試的提醒（新模型自己會跑）；③為了防越權而寫的強硬「先問我」用語（GPT-6 Astra 可能太當真、在你希望它繼續的地方停下）。這一條講的是「該不該做」的邊界，下一條講「做到哪算完」的停點。延伸：倉庫裡的 skill 會被別人用不同模型讀，寫時要想「誰會讀」；文章最後建議直接請新模型依這些原則稽核你的指令集。（OpenAI 開發者部落格）
- [[define-completion-upfront]]：接上一條的「停點」：GPT-6 Astra 比 GPT-5.6 Sol 更容易做出第一版就回來等審查。解法是開工前先定義「什麼叫做完」：要不要把實作跑起來、檢查結果、修掉失敗，都明寫進請求；「第一版後停下來審」這種要求會把模型拉向更早的停點，先想清楚那個審查點是不是真的需要。想讓它多探索，就說要探什麼、探到哪停。（OpenAI 開發者部落格）

## 我的立場

> 針對本篇核心主張的表態；空槽待 Simon 事後填、未表態即留白，芙莉蓮不代擬。（2026-09-17 錨點由 5 條合併為 4 條：原第 1、4 條合併；Simon 同日親口填表態。）

1. 模型越強，過去為了牽著舊模型走而寫的 skill、規則、「先問我」邊界用語，越可能從幫助變成限制（新模型甚至會把那些句子當真而提早停）；換模型時該整批重審，甚至直接請新模型來稽核。
   - **我的表態**：同意。有時候為了模型的強度，寫 skill 的時候會寫得比較細、也比較緊一些，來限縮模型的自由發展能力；但當模型越來越強的時候，skill 也許要適時調整一下，搞不好效果會更好一點。（2026-09-17）
   - **芙莉蓮評比**：站得住，補一層分類：不是所有「緊」都該隨模型變強而鬆。安全／授權類的緊（財務寫入器、第三方執行體安全入口、非 Simon 內容不寫常駐檔）是防越權，跟模型強弱無關，換模型也不放；該重審的只有「防舊模型做錯」那類。Simon 同日立的「CORE_RULES 指令債稽核」卡（A5＋A7）正是先做這個分類再判。另外「效果會更好」目前是文章主張、沒有數據，要等稽核後實測才知道。

2. skill 描述應盡量短、只講清楚「什麼情況該用」；描述太長或 skill 太多時 Codex 會截短描述，模型反而更難挑對。
   - **我的表態**：同意。因為我有發現有時候 AI 會變懶、不讀完全部。（2026-09-17）
   - **芙莉蓮評比**：結論對、機制要分開。描述太長的問題主要是機械截短：Codex 對描述欄有長度上限，超過就截掉、模型根本看不到後面；再加上描述越多越難比對。「AI 變懶不讀完」是另一件事，像 2026-09-13 harness 健檢抓到的分段讀長檔漏段，屬審查者讀檔紀律。兩者都真實，但縮描述只解前者；後者靠已讀範圍申報這類機制擋。

3. 「每次編輯前先讀某幾份文件」這類無條件必讀清單應改成條件式指向：做哪類任務才看哪份文件。
   - **我的表態**：同意，但是要注意如果條件寫太窄會少讀。（2026-09-17）
   - **芙莉蓮評比**：確認，而且顧慮點到要害。補一個判準：某條「無條件先讀」如果是因為漏讀曾出過事才寫的（例如「判讀工具回傳前先 Read 三層模型」源自 2026-06-01 M05），條件至少要寬到涵蓋那次事故的情境，不然等於把教訓刪掉。這也是為什麼 A6 併進 A5 卡時要求先列「改後哪些情境會漏」再拍板。

4. 開工前先定義「什麼叫做完、探索到哪停」並寫進請求；需要它繼續跑已知安全的流程（例如本機測試），就在 AGENTS.md 明確授權。
   - **我的表態**：同意，本來就要有限制條件，不然會越做越多、越改越多。（2026-09-17）
   - **芙莉蓮評比**：確認。前半「定義做完與停點」今天已落地成派工模板的停止點（A8）。後半「在 AGENTS.md 明確授權跑安全流程」在 Simon 這邊其實已是現況：Claude 端全域 permission 為 bypass、feedback「GO 之後別問」；所以這條對他而言新增的只有前半。「越改越多」正是停止點要擋的，判準是驗收條件可判定、到點就停。

## 原文要點
- 模型越強，過去為了牽著它走而堆出的 skill、AGENTS.md、任務提示詞就越該重審；到 GPT-6 Astra 這一版尤其重要。
- skill 描述：越短越好、只講何時適用；描述太長太多時 Codex 會截短，模型更難挑對；描述互相矛盾或過度強調會讓模型載入沒用的指令。OpenAI 已更新 `$skill-creator` 指引來對付這些失敗型態。
- 漸進揭露：讀 skill 有脈絡成本，多流程 skill 的根文件做成最小路由器、指向附屬文件與腳本。
- 食譜式指引過時：模型已能處理細微差異與模糊，過度具體反而拖低結果；倉庫裡的 skill 會被別人用不同模型讀，寫時想清楚誰會讀。
- AGENTS.md：常回頭問每條還需不需要；「每次編輯前先讀三份文件」對改錯字太過頭，改成「哪類任務看哪份」；文件本身要維持更新；舊模型要催才跑測試、Astra 自己會跑，同樣指令變成多跑。
- Astra 偏保守，可在 AGENTS.md 對已知安全的流程明確授權（例：用拋棄式測試資料且不碰正式環境的本機測試，跑、修、重跑都不必逐步問）。
- 邊界：為舊模型寫的強硬「先問我」用語，Astra 會太當真而提早停；換模型時重寫這些語句。
- 持續性：Astra 比 GPT-5.6 Sol 更容易在第一版後停下；開工前定義完成、把「跑起來、檢查、修失敗」寫進請求；「第一版後停下來審」會拉早停點；要探索就說探什麼、到哪停。
- 收尾：請 Astra 依本文稽核你的指令集，然後去做以前不敢做的事。

## 盲點與保留
**缺口／矛盾**：
- 原文建議「為舊模型寫的強硬『先問我』用語，換到更對齊的模型時考慮改掉」，但沒有區分可逆與不可逆動作：刪資料、對外送出、付費呼叫這類仍需要硬邊界，文章把「先問我」一律當成舊模型的遺產。對照 reading 2026-06-05-dustin-claude-code-harness-cleanup：Dustin 的重整是刪重複、衝突與冗長內容（[[agent-harness-hygiene]]），不是放鬆邊界；兩篇方向不同、不算矛盾，但本篇漏了「哪類邊界不該隨模型升級而放鬆」這條線。
  - **Simon 回應**：（待補：同意／不同意這個保留＋為什麼）
- 「描述太長或 skill 太多時會被自動截短」只講 Codex 的行為；Claude Code 端是否同樣截短，原文沒證據，[[skill-description-precision]] 對 Claude Code 的適用程度因此帶著一個未驗證的假設。
  - **Simon 回應**：（待補）
- 與 reading 2026-05-14-blocktempo-claude-code-12-rules 有張力：那篇（[[claude-md-12-rules]]）主張用 12 條契約式規則把錯誤率從 41% 降到 3%，是「加規則有量化效益」；本篇主張「換模型先刪規則」，卻沒給任何數字（錯誤率、脈絡用量都沒有），「還需不需要」的判準只有一句「常回頭問自己」。兩篇並列時，讀者拿不到「哪些規則該留」的判準。
  - **Simon 回應**：（待補）
**過度吹捧／該打折**：
- 「GPT-6 Astra 是我們最對齊的模型、判斷力好很多、不確定安全就不會做——所以你該這樣對待它」是廠商對自家模型的宣稱，沒有第三方驗證；拿它當前提去放鬆邊界語言，風險由使用者承擔。事實內核：更強的模型確實較少需要食譜式指引；行銷層：「相信它的判斷、去做以前不敢做的事」。
  - **Simon 回應**：（待補）
- 收尾建議「請 Astra 依本文稽核你的指令集」：由被指令約束的模型來稽核約束它的指令，有自利偏誤——模型會傾向刪掉限制自己的規則；原文沒提要人工複核稽核結果。
