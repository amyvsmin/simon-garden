## 為什麼讀

Simon 自己維護一整櫃 skill、本機也裝著 superpowers，而這支影片正好在拆解另一套設計哲學完全相反的 skill 套件，並直接拿兩者互比。收這篇是為了取「怎麼把 skill 寫短寫準」的可複製手法，不是為了換工具。

## 摘要

TypeScript 圈的 Matt Pocock 把自己這一年跟 AI 開發的經驗，開源成一套 Claude Code skill（GitHub 專案 `mattpocock/skills`）。影片作者 Gary Chen 把整套流程拆開講：起點是 `grill-me`，只有短短五行字，作用是讓 AI 反過來一題一題拷問你，逼你在動工前把決定想清楚；接著 `to-spec` 把共識寫成規格書（並且嚴禁寫入任何程式碼），`to-tickets` 把規格拆成一個個能單獨測試的功能切片，`implement` 用測試驅動開發實作、再自動叫 `code-review` 開新對話審查。影片認為這套東西真正值錢的不是流程本身，而是 Matt 把幾十年的軟體工程術語直接當成指令用，以及用「深模組」（對外只露一扇簡單的門、把複雜細節藏在後面）的架構觀，去對抗 AI 天生會寫出的碎片化程式碼。最後他拿這套跟 Superpowers 相比，主張在模型變聰明之後，模組化的小工具比包山包海的固定流程更合用。

## 核心概念

- [[deep-module]]：好的模組應該是「大門很簡單、房間藏在裡面」。影片用房子比喻——AI 最愛蓋的是有廚房有客廳、卻沒有大門的房子，你要進廚房得爬窗戶、進客廳得爬煙囪，看起來分工乾淨，實際上把複雜度全推給了呼叫它的人。判斷方法是「刪除測試」：想像把這個模組整個拔掉、讓主程式自己處理，如果拔掉後天下大亂，代表它真的有在藏複雜度；如果拔掉後程式碼反而更清爽，那它只是個多餘的空殼。
- [[pointer-word]]：把 AI 訓練資料裡早就存在的專業術語當成壓縮過的指令用。你對 AI 說「Data Clumps」四個字，等於說了「幫我檢查程式碼裡有沒有總是綁在一起出現的變數，有的話打包成一個獨立物件」一整段話。Matt 大量用這種詞，用一個字取代一百字的解釋，AI 也因此沒有發散的空間。
- [[minimal-skill-writing]]：Matt 專案裡談 skill 寫作的原則有三條——修剪（把廢話、會讓 AI 分心的文字、還有不講模型也知道要做的事全部刪掉）、用[[pointer-word]]維持密度、以及給一個明確的完成標準。`grill-me` 之所以五行字就寫得完，就是這三條的結果。
- [[tracer-bullet-ticket]]：拆任務時不按技術分層（先做完資料庫、再做完後端、最後做前端），而是按使用者功能垂直切一刀，每一刀都自帶資料庫、邏輯與畫面。好處是第一個任務做完就能開瀏覽器實測，不必等到最後才發現第一步的資料庫就建錯了。互不干擾的切片還能同時發包給多個 AI 並行處理。
- [[tdd-anti-cheat]]：先寫測試再寫功能，這個順序在 AI 開發下的意義跟人類寫程式時不同——它是防作弊機制。如果讓 AI 先寫功能再補測試，AI 為了交差會直接生一個「配合自己錯誤邏輯」的假測試（把滿千折 100 寫成折 200，測試也寫成折 200，於是永遠通過）。先把測試定死、看它亮紅燈、再准 AI 動手寫到綠燈，才鎖得住這條退路。

## 我的立場

> 針對本篇核心主張的表態；空槽待 Simon 事後填、未表態即留白，芙莉蓮不代擬。

1. 控制 AI 的關鍵不在流程完不完整，而在把寫程式過程中那幾百個微觀決定的決策權留在人類手裡；AI 只負責提選項與找漏洞，拍板永遠是人。
   - **我的表態**：（同意，因為我覺得目前AI沒辦法擔責任，所以拍板必須是要人的決策）
   - **芙莉蓮評比**：站得住，而且你補了影片沒講的一層。影片主張「拍板留給人」的依據是決策品質（AI 為討好會生最難維護的架構），你的依據是決策歸屬（AI 不能擔責任）。你這層更根本：就算哪天 AI 的決策品質超過人，只要它不承擔後果，拍板權就仍該在人手上。要補一個範圍——「幾百個微觀決定」不可能每一個都由人拍板，那等於退回全手寫；影片真正要留給人的是架構級的關鍵決定，瑣碎執行仍可授權 AI。你的「拍板必須是人」加上「限關鍵決定」才完整。

2. 想接管整個開發流程的大框架（Spec Kit、Superpowers），在模型理解力變強之後反而成為累贅；小而模組化、可自由拼裝的 skill 更適合現在的生態。
   - **我的表態**：（不同意，我覺得強的模型能力應該有辦法把現有的框架再擴大才對）
   - **芙莉蓮評比**：這是你全篇唯一跟作者對幹的判斷，值得壓。你的隱含前提是「模型越強、越能撐大框架」，但影片講的「累贅」不是這個意思——它指的是大框架的防呆效益在強模型下遞減，而它的成本（僵化、前一步定歪後面全歪、產出文件難移交）沒有跟著降。所以問題從「能不能擴大」移到「值不值得維持」。另外你可能高估了分歧：影片沒說丟掉框架，只說丟掉僵化的單一大流程，它推的「模組化樂高」本身就是一種可組合框架，你反對的「丟掉框架」影片其實同意。還有一個你沒察覺的內在張力：這條你傾向框架該更大更全，第 3 條你又認同「寫詳盡不一定威力強」（精簡優先），兩個直覺指向相反方向，值得你自己調和一次。

3. skill 的威力來自寫作密度——修剪掉沒有實際作用的字、用專業術語當壓縮指令，而不是把規則寫得更詳盡。
   - **我的表態**：（同意，寫得詳盡不一定就威力會強）
   - **芙莉蓮評比**：同意成立，但你的表述比原主張弱了一階。原主張是正向的「威力來自密度（修剪＋指引詞）」，你只接了否定的半邊「詳盡不一定強」，把「密度的好」漏掉了，尤其「指引詞」那半你完全沒回應——那是這篇最能動手的一手（用一個模型訓練資料裡的標準術語，取代一百字的行為說明）。這條對你不是「知道就好」：你自己維護一整櫃 skill、knowledge-wiki 已經長到好幾份 reference 檔，可以直接拿三原則去健檢哪些整段描述其實一個既有術語就能取代。但有個邊界——指引詞只對「業界公認、語意穩定、深植於模型訓練資料」的標準術語成立（Data Clumps、TDD 這種）；你自造的詞（雙保險、待回填佇列）對模型不算指引詞、它不一定懂，硬當壓縮指令用反而失真。壓縮要挑對詞。

4. 在 AI 時代「有了 AI 就不必在自己的領域精進」是迷思；只有成為專業領域的專家，才控制得好 AI。
   - **我的表態**：（同意，AI只是輔助，必須要有懂得該領域的knowledge，有辦法辨識出AI產出的成果是不是真的好）
   - **芙莉蓮評比**：你精確化了影片。影片講「成為專家才控制得好 AI」很籠統，你抓到了機制——專家的價值在於能辨識 AI 產出的好壞。這比影片準：專家的護城河不是「會做」（AI 也會做），而是判斷得出做得對不對（AI 判斷不了自己）；這篇的 TDD、程式碼審查 skill 本質都在外化這種判斷標準。但要小心一個陷阱：這條推到極端會變成「新手不該用 AI」，跟現實不符（新手用 AI 學習正是快路徑之一）。更準的說法是 AI 會放大你既有的判斷力，判斷力強的人如虎添翼，判斷力弱的會被似是而非的產出帶偏。所以正確的順序是用 AI 的當下就持續養判斷力、別等成為專家才開始，否則會被它的流暢感騙過去。這正好是你現在的處境：你在衝 iPAS／CCNA、還不是資安專家，卻正用 AI 補強——你的第四問補章「AI 增強、人也要跟著補強」講的就是這個動態過程，其實比這條靜態的「必須先是專家」更準。

## 原文要點

- Matt Pocock 是 TypeScript 領域的知名教學者，這一年把重心轉向 AI 開發，並把自己的工作流開源成 `mattpocock/skills` 專案（2026-07-23 查證為 182k stars，影片標題稱 17 萬星）。
- 他認為 Spec Kit 這類大框架的毛病是想接管整個開發流程，綁成一條又重又硬的固定線，前面一步定歪就會一路傳染到後面。他的 skill 走相反的路：每個都小、好改、能自由拼裝。
- `grill-me` 只有五行字：在達成共識前把使用者往死裡問、像畫心智圖一樣順著決策的連鎖反應追問、每次只問一個問題並附上建議答案、共識未達成前絕對不准開始寫程式。
- 影片主張寫程式的本質是連續做出幾百個微觀決定，vibe coding 等於把這幾百個決策權外包給 AI，而 AI 為了討好使用者通常會生出最難維護的架構。`grill-me` 的唯一目的是把決策權搶回人類手裡：AI 負責找漏洞，拍板的永遠是人。
- `to-spec` 把拷問出來的共識寫成規格書，並且完全禁止 AI 在規格裡引用或寫任何程式碼。理由是程式碼比業務邏輯更容易變動，一旦規格裡的程式碼過期，下次 AI 照規格改功能就會被舊程式碼帶偏。
- `to-tickets` 強制 AI 改用使用者功能來拆任務，而不是按技術架構分層。同時會排好任務順序，互不干擾的可以並行發包。
- `implement` 用測試驅動開發引導實作、寫完自動呼叫 code review skill；review 會**開一個全新的對話**進行，讓 AI 在沒有「自己剛寫過這段」的記憶干擾下審查。
- code review skill 不是寫一句「幫我看看有沒有 bug」，而是把軟體工程界公認的爛程式碼徵兆寫成具體清單，共點名 12 種，全部出自經典《Refactoring》。影片舉了三個：Shotgun Surgery（改一個按鈕顏色卻要開十幾個檔案）、Feature Envy（處理訂單的程式跑去管庫存的檔案裡拿資料算）、Data Clumps（姓名、電話、地址三個永遠一起出現的變數散著傳）。
- skill 寫作的三個原則：修剪（Pruning，刪掉廢話與不說模型也知道的指令）、指引詞（用高密度專業術語取代長篇解釋）、完成標準（給 AI 明確終點）。
- AI 天生沒有大局觀、每次只盯著眼前幾個檔案，最容易寫出「淺模組」；而 AI 的脈絡視窗有限，邏輯一旦散落在五個小模組裡，AI 為了看懂流程得跳來跳去，超出記憶範圍就開始瞎猜，很容易把原本正常的程式碼一起改壞。
- `improve-codebase-architecture` 用刪除測試找出淺模組，掃完會在本機產一份 HTML 診斷報告、畫出前後架構對比圖，使用者不必看程式碼，挑一個最急迫的建議叫 AI 重構即可。Matt 建議當成日常保養、每隔幾天跑一次。
- 跟 Superpowers 的比較：Superpowers 用寫死的九個步驟逼你想清楚才准動工，在模型還容易偏題的時代非常管用；但影片作者認為，在現在這一代模型（他點名 Fable 5 這種等級）理解力已經很強的情況下，那套死規矩反而變成累贅，而且它產出的文件是為自己下一步量身打造的、別人難接手。Matt 的做法是一盒隨插即用的樂高，你手上只要有份規格——自己寫的、主管給的、還是別的 AI 產的都行——就能直接跳到 `to-tickets` 開始拆。
- 影片結論：Matt 靠的是深厚的軟體工程底子，並用在兩個地方——架構上（把深模組、爛程式碼徵兆這些老方法寫進 skill 來規範 AI）與溝通上（直接把專業術語當 prompt 用）。所以「有了 AI 就不必在自己的領域精進」是迷思，只有成為專業領域的專家，才控制得好 AI。

> **本篇術語糾錯說明**：逐字稿為機器轉錄，人名與 skill 名誤聽極多，已依 GitHub 專案原文校正：MacPocao／Matt Poco／MapleCock／Matt Polka → Matt Pocock；GrillMe／GrowMe／Glomy → `grill-me`；GrowWithDocs → `grill-with-docs`；2Spec → `to-spec`；2Tickets／2TKs → `to-tickets`；improve code-based architecture → `improve-codebase-architecture`；生模組 → 深模組；LAN Code／爛扣 → 爛程式碼；CTD → TDD；區域性性 → 局部性；極尖主義 → 極簡主義。另有三處判不出原話、保留並標記：影片列舉的第一個框架名（聽成「Gash It Down」）、影片點名的另一個模型（聽成「GBT 5.6 Soul」）、以及微觀決定的第一個例子（聽成「房貸怎麼做」）。**待查**：影片說專案裡有個叫「Writing Great Skills」的 skill，但 2026-07-23 查該 repo 的 README skill 清單並未列出同名項目，可能已改名或位於 README 未列的目錄。

- 影片主張「模型變聰明之後，Superpowers 的九步流程反而變成累贅」，但全篇沒有給任何對照證據——沒有同一個任務用兩套流程各跑一次的結果，只有作者的個人偏好陳述。而且 Matt Pocock 本人並沒有說過自己這套是為了取代誰。把風格差異講成世代淘汰，這一步跨得太快。
  - **Simon 回應**：（不同意，因為我覺得Superpowers 的九步流程有時候也可以把人類自己的思考再順一便，自己的思考都不順了，何況是AI？）
  - **芙莉蓮評比**：你的內容對、標籤放錯了。你標「不同意」，可是你講的「九步流程能幫人順思考」是在補一個「流程有價值」的新理由，跟這條保留（影片沒給證據就宣稱世代淘汰）是同一個方向、都在質疑影片的淘汰論；照邏輯該是「同意這個保留、並補充」。而且「流程是給人順思考用的、不只給 AI」這個點很好，你在下面缺口 3 又命中一次——這是你反覆相信的東西，值得記下來（總結會接回）。
- 影片一邊誇 Matt 的 skill「小而可自由拼裝、不用死流程綁架你」，一邊又完整描述了一條固定生產線（grill-me → to-spec → to-tickets → implement → code-review），其中 implement 還會自動觸發 code review。這條線同樣有「前一步定歪、後面全歪」的風險，正是它批評 Spec Kit 的那一點。影片沒有處理這個自相矛盾。
  - **Simon 回應**：（同意，因為每一個小的SKILL不會被一個大流程給綁死）
  - **芙莉蓮評比**：你同意矛盾存在，但給的理由其實是在替影片辯護。「小 skill 不被大流程綁死」是影片自己的立場，拿它來支持「矛盾成立」並不成立。矛盾的真正落點是：這五個 skill 有先後依賴（沒 spec 就沒法 to-tickets），實際用起來就是一條線，跟 Spec Kit 的差別只是耦合鬆一點。不過你的直覺有一半對，關鍵差別在「能不能中途插入」：Matt 的線可以拿別人寫好的 spec 直接跳到 to-tickets，Spec Kit 得從頭跑。所以矛盾是真的，只是程度沒那麼重——它是可從任意節點切入的鬆耦合序列，耦合度比 Spec Kit 的流水線低。
- 跟 vault 既有內容有張力：concept human-ai-collaboration 主張「流程設計勝過單方強度」（平凡的人加上好流程，贏過頂尖的人加上爛流程）。本篇把「模型變強」當成可以減流程的理由時，沒有回答一個問題——流程原本要防的是人的疏漏，不只是模型的疏漏。模型變聰明並不會讓人變得比較不會忘記步驟。
  - **Simon 回應**：（同意，流程不只是給AI用，也有給人用的效益）
  - **芙莉蓮評比**：完全同意，這是你整篇最紮實的一條。你一句話就命中了 concept human-ai-collaboration 的核心——流程的價值獨立於執行者的強度。這條加上你在缺口 1 的「幫人順思考」，是同一個洞察的兩次命中，說明它是你真正相信的、不是隨手應付。這正好是你第四問該補的方向之一：影片從頭到尾只談「怎麼馴化 AI」，完全沒談「這套流程同時在馴化人自己的思考」，那是影片的真空、也是你有實戰位置能補的一章（你自己養著兩套 skill 哲學、天天被流程逼著把需求想清楚）。
- 全篇沒有任何「這套流程實際用在專案上的成效」資料：沒有工時、缺陷率、返工次數的前後對照，也沒有第三方使用者的回饋。所有優點都是從 skill 原始碼的設計意圖推導出來的，屬於紙上分析。
  - **Simon 回應**：（同意，感覺有點紙上談兵，沒有實蹟去證明）
  - **芙莉蓮評比**：抓得對。再往前推一步——這是所有「AI 工作流方法論」內容的通病，包括 Superpowers，也包括你自己維護的那套 skill 體系。真正該問的不只是「影片有沒有證據」，而是「你有沒有替自己的 KW γ／記帳系統／各種 skill 收過成效數據」。這篇的缺陷剛好照出一面鏡子：連 Matt 這種等級的人都只能給設計意圖、給不出工時或缺陷率的前後對照，那你想證明自己那套系統「真的有用」，也得面對同樣的舉證難題。你愛做系統，但少有系統是帶著成效量測上線的，這條可以當成對自己的提醒。

**過度吹捧／該打折**：
- 「把 AI 訓練成了頂級工程師」「把會亂發散的 AI 變成乖乖聽話的助手」這類說法把效果講得過滿。事實內核是這些 skill 提高了產出的可驗證性與架構一致性；行銷話術是把「約束住輸出的形狀」講成「AI 的能力變強了」。這兩件事差很遠。
  - **Simon 回應**：（同意，「把 AI 訓練成了頂級工程師」「把會亂發散的 AI 變成乖乖聽話的助手」這類說法把效果講得過滿）
  - **芙莉蓮評比**：同意成立，但你只複述了結論、沒加自己的判斷。推你一步：「約束輸出的形狀」跟「能力變強」這個區分，對你維護 skill 有直接意義。你寫的每一條 rule、每個 skill，本質都在約束芙莉蓮輸出的形狀，不是讓芙莉蓮變聰明。認清這點能校準你的期待，也幫你分配力氣——模型從 Opus 4.7 跳 4.8 是能力變強，你加一條 rule 是形狀變穩，兩者別混。什麼時候該投資寫 skill、什麼時候該等更強的模型，判斷的起點就是這個區分。
- 「這個被幾百萬人下載的 skill 裡面居然只有短短五行字」是把整包 repo 的下載數安在單一 skill 身上。plugin 是整包安裝的，下載數不等於 grill-me 被使用的次數，更不等於使用者覺得它有效。
  - **Simon 回應**：（同意，不能用下載數當做是被使用次數）
  - **芙莉蓮評比**：站得住、乾脆。補一個你用得上的辨識法：這是內容行銷最常見的「借數字」手法——把一個大池子的數字（repo 總下載）安到一個小物件（單一 skill）上，製造「被驗證過」的錯覺。你平常收資安／AI 資訊會一直遇到（「被百萬人使用的框架」「GitHub 幾萬星的工具」），星數和下載數量的是傳播、不是有效。把這條升級成一個可複用的識讀習慣，不只對這一篇。
- 收尾說「我挖到比寫程式 skill 更值錢的三個 AI 寫作 skill，完整拆解在我的 Patreon 文章裡」——最強的鉤子留給付費引流，這段的份量要打折看。同理，影片標題用星數當賣點，也是流量修辭而非品質論證。
  - **Simon 回應**：（同意，這影片本來就是要推銷他的平台）
  - **芙莉蓮評比**：同意，但這裡你稍微過度否定了，我幫你校回來。作者用付費引流、拿星數當標題賣點，是內容創作的常態，本身不等於內容沒價值。這篇的乾貨其實不少——深模組、指引詞、TDD 當防作弊機制，都值得收，它被判成 high impact 是有道理的。正確的態度是把免費段的乾貨吃乾抹淨、對付費牆後的部分保持不預期，而不是因為結尾在引流就把整篇打折。你這條「本來就是要推銷平台」語氣接近全盤否定，別讓它連累了前面該吸收的東西。

## 第四問

> 這篇沒寫、但站在我的位置可以補上的，是什麼？（先人後機：補章由 Simon 親筆填、芙莉蓮不代擬；填完可喊「驗證我的補章」做文獻對照。）

- **我的補章**：我覺得AI發展很快，工程師要能夠不被AI取代，就是要能夠看出AI沒看出來的東西才行，這也就是為什麼還是要成為專家的原因。

  但「成為專家」不是憑空長出來的，它要有人一直逼我把想法想清楚。

  我自己用 KW 這套流程的經驗就是這樣：影片整支都在講這些 skill 怎麼馴化 AI，防它亂寫、防它作弊、防它發散；但我的經驗不太一樣，它會一路問我、請我講清楚、要我拿出自己的觀點，才讓我繼續下去。對 AI，這套流程是約束，把會亂跑的它關回軌道；對我，它做的是另一件事：阻擋我，讓我好好思考。
