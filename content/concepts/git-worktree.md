## 定義

讓同一個 Git 專案在硬碟上同時展開成多個獨立工作目錄的機制。每個工作目錄各自停在不同的分支上，但共用同一份版本歷史，所以可以同時攤開兩個以上的版本，不必來回切換。

## 關鍵面向

- **跟分支的差別在「同時」**：分支像同一張辦公桌旁邊的平行時空切換鈕，按一下桌面內容整個換掉，同一時間只看得到一個版本；工作樹則是直接在旁邊擺第二張實體桌子，兩個版本可以同時攤開。分支解決的是「隔離」，工作樹解決的是「並行」。
- **共用版本歷史、不共用檔案內容**：多開出來的目錄不是複製一份專案，而是同一個倉庫的另一個出入口，提交（commit）與分支是共用的：在 A 目錄 commit 之後，B 目錄用 `git log 那條分支` 立刻查得到這筆提交。但每個目錄的實體檔案各自獨立，A 目錄存檔、甚至 commit 了，B 目錄的檔案都不會自動跟著變；B 要把那條分支合併（merge）或 cherry-pick 過來才拿得到改動；Git 預設不准兩個工作樹同時切到同一條分支。所以兩個代理各掛一個工作樹，彼此的未提交存檔看不到，這正是它能防撞的原因。
- **多個 AI 代理同時開工才會用到**：一個人一次通常只做一件事，所以過去工程師很少用它。但同時派兩三個代理各做各的功能時，若共用一個工作目錄，就會出現「明明在資料庫那條分支上，卻混進了改介面的存檔」這種狀態錯亂。
- **成本不是零**：每開一個工作樹就多一份實體檔案，磁碟與環境（套件安裝、設定檔）都要各自準備一次。只有真的要並行時才值得開，單線開發用分支就夠。

## 應用場景

- Simon 工作場景：同時派多個 Claude Code 子代理改同一個 repo 時，讓每個代理掛自己的工作樹，避免互相覆蓋；Workflow 的 `isolation: "worktree"` 參數就是在做這件事。
- 一般場景：一邊開發新功能、一邊要緊急修主線的小錯字，不必把手上做到一半的改動先存檔或丟掉。
